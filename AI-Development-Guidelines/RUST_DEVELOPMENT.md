# Rust 通用 AI 辅助开发规范

## 适用方式

本规范适用于 Rust 项目的新增、修改、修复和代码审查，可作为开发任务的附加指令。
目标是减少定位、阅读、生成和返工成本，同时保持正确性、可维护性与可验证性。

- 项目明确要求、已有接口和仓库配置优先；以下规则提供未明确事项的默认做法。
- 先阅读核心规则，再按任务阅读有关章节；不必每次遍历全部代码和文档。
- 遵循项目的 edition、MSRV 和 toolchain；不因工具更新顺带升级版本。
- 小程序保持简单；工作区、分层和公共抽象随实际需求增加。

## 核心规则

1. **围绕任务修改。** 保留无关行为和用户已有改动；不顺带重构、改名或格式化。
2. **让相关代码容易找到。** 按职责命名和组织，避免万能模块与过度拆分。
3. **让接口可独立理解。** 明确输入、输出、错误、所有权和必要的不变量。
4. **优先直接实现。** 先用具体类型、普通函数和清楚的调用关系解决问题。
5. **限制变化传播。** 内部实现调整尽量不迫使调用方、配置或其他 crate 同时修改。
6. **使用局部补丁。** 避免重复生成整份未改变的文件，以及大段复制现有逻辑。
7. **用检查减少返工。** 根据受影响行为选择构建、测试和分析范围。
8. **不以可靠性换 token。** 保留必要的类型、错误处理、资源管理和验证，并如实报告结果。

## 代码组织与接口

- 一个模块围绕可说明的职责组织；相关实现尽量放近，避免追踪功能需要频繁跨文件。
- 文件长度用于提示职责是否混杂，不设机械行数上限，也不为缩短文件制造无意义转发层。
- 将计算逻辑与文件、网络、时钟等外部操作适当分开，让核心行为容易单独验证。
- 默认保持私有；按需使用 `pub(crate)` 或 `pub`，避免扩大不必要的兼容性承诺。
- 公共接口注明错误条件、重要副作用及约束；内部直观函数不要求重复描述代码的注释。
- 用结构体、枚举和命名表达数据含义；避免含义不明的长元组、布尔参数组合和字符串状态。
- Trait、泛型和额外 crate 应解决实际复用、边界或构建问题，不为假想扩展预先设计框架。
- 修改公共接口时检查调用者、文档和测试，说明兼容性影响。
- 保留简短的模块导航及开发命令；随职责或命令变化更新，不维护逐文件实现说明。

## Rust 专项规则

### 所有权与类型

- 先理清数据由谁拥有、借用持续多久，再决定引用、移动和共享方式。
- 优先简单的所有权结构和具体类型；编译器可推导时不增加无意义的生命周期标注。
- 生命周期和泛型用于表达真实约束，避免为减少少量重复而引入难以阅读的类型层级。
- 借用参数通常优先考虑 `&str`、`&[T]` 等合适视图；需要取得所有权时在接口中明确表达。
- `clone` 并非禁用操作；判断数据大小、调用频率和简化程度，避免在热点中无意复制大量数据。
- 不用 `Arc<Mutex<_>>` 掩盖不清楚的所有权；确实需要跨线程共享可变状态时才引入同步机制。

### 错误与边界

- 预期可能失败的操作返回或处理 `Result`；可能缺失的值使用合适的 `Option` 语义。
- 使用 `?` 时保留必要的错误上下文；在合适边界记录或转换错误，避免各层重复记录。
- 不静默丢弃失败，也不把解析错误、文件故障等失败伪装成正常默认值。
- 外部输入在边界验证，内部复用已建立的约束；日志不记录密钥或不必要的完整敏感数据。
- `unwrap`、`expect` 可用于测试及有明确依据的不变量；不能代替对外部输入失败的处理。
- 不变量不明显时解释成立依据；`expect` 的消息说明预期成立的条件。
- 注意索引、整数范围、边界长度和空输入；检查强度由数据来源和使用场景决定。

### 异步、并发与底层代码

- 按实际 I/O 或并行需求采用异步与并发，沿用已有运行时，不为统一风格改写同步代码。
- 共享状态说明同步约束；缩短持锁范围，尤其审查跨 `.await` 持锁是否必要及安全。
- 根据任务处理取消、超时和后台任务退出，避免无限等待及无人管理的任务。
- 将 `unsafe` 和 FFI 限制在小而清楚的边界；优先对外提供可安全调用的封装。
- 说明指针有效性、生命周期、别名、线程约束及资源释放责任，并在相关操作处注明安全依据。
- 不为消除编译错误随意增加 `unsafe`；涉及 FFI 时遵循既定 ABI、错误传递和释放约定。
- 优先普通函数和已有派生宏；自定义宏应带来明确收益，避免隐藏关键控制流与副作用。

### Cargo 与依赖

- 沿用现有 workspace、feature 和依赖策略；引入依赖前检查标准库与已有依赖能否满足需求。
- 根据目标平台、MSRV 和实际使用范围选择依赖及 feature，不默认启用所有可选能力。
- 遵循仓库的 `Cargo.lock` 提交策略；不因任务无关的构建顺带刷新整个依赖图。
- 不把本机路径、隐式环境变量或开发机特有工具变成未经说明的构建前提。

## 读取与修改流程

1. 确认任务范围，检查有关项目指令、`Cargo.toml`、工具链配置及已有检查命令。
2. 先搜索符号、入口或错误信息，定位目标实现及有关调用者。
3. 阅读理解行为所需的类型、错误路径、测试和配置；信息不足时继续扩展上下文。
4. 简要确定修改范围后提交局部补丁；新代码沿用相邻实现的命名与风格。
5. 检查差异，排除误删、重复逻辑和无关变更，再执行相应验证。

- 不以“少读”为由猜测函数签名或 crate 能力；不确定的行为查阅实际源码或对应版本文档。
- 优先一次读取相关的少量文件，避免逐行调用工具，也避免无差别倾倒全仓库内容。
- 使用编译器诊断定位类型和借用问题；理解原因后修改，不反复堆叠转换、复制或同步包装。
- 局部调整足以解决问题时保持范围；确需扩大修改时说明它与目标行为的关系。
- 回复中列出关键变化和证据，不重复粘贴已写入文件的整份代码。

## 验证

优先运行仓库已有脚本或 CI 对应命令。以下是范围选择示例，按项目配置和工具可用性调整：

```sh
cargo check -p package_name
cargo test -p package_name test_name
cargo fmt --all -- --check
cargo clippy -p package_name
```

- 将示例中的包名与测试筛选项替换为实际值；确认筛选后确实执行了目标测试。
- 先检查受影响包、测试和目标；公共接口、共享依赖或集成行为变化时扩大验证范围。
- 验证任务实际使用的 feature 与 target；需要覆盖不同配置时选择有意义的组合。
- 不默认使用 `--all-features`、所有平台或 `-D warnings`；仓库有明确要求时遵循。
- `cargo check` 不等于测试通过；Clippy 与格式检查也不能代替行为验证。
- 修复缺陷或修改重要行为时增加有价值的回归测试；低影响文档、格式等修改不强制新增测试。
- 测试关注可观察行为、边界和失败路径，避免仅重复实现或过度绑定内部结构。
- 格式检查发现无关历史问题时单独报告；不要据此格式化整个仓库。
- 工具缺失、目标不可用或环境限制导致检查未执行时，明确说明未验证范围。

## 完成标准

- 需求涉及的行为已实现，相关调用方和说明保持一致。
- 差异集中于任务，接口、所有权和错误处理足够明确。
- 已完成与变更范围相匹配的可用检查，并确认结果。
- 最终简述改动、验证结果及剩余限制；区分已通过、未执行和仍然失败的检查。
- 不将“能够编译”“尚未发现问题”或“测试未运行”表述为功能已全面验证。
