# Python 通用 AI 辅助开发规范

## 适用方式

本规范用于 AI 辅助编写、维护和审查 Python 项目，可直接作为项目开发约束。

- 项目明确要求、兼容性承诺和现有工具配置优先；以下条目作为缺省规则。
- 按当前任务阅读相关章节；先定位实现、接口和验证入口，再补充必要上下文。
- 优化目标是完成一次正确修改的总成本，包括读取量、生成量、工具往返和返工。
- 保留必要的类型、校验、错误处理和测试，不以省 token 为由降低正确性。

## 核心规则

1. **先明确行为。** 确认输入、输出、失败方式和兼容性边界，沿用已有约定。
2. **控制修改范围。** 优先局部补丁；不顺带重命名、格式化或重构无关代码。
3. **保持调用直接。** 优先普通函数和明确参数，仅在解决真实重复或扩展需求时抽象。
4. **围绕职责组织。** 相关实现放近，模块边界清楚，使修改一个功能无需理解整个项目。
5. **使用明确契约。** 类型和数据模型表达约束，外部输入在边界验证。
6. **让失败可定位。** 保留异常原因和业务上下文，不静默吞错或伪造成功结果。
7. **按风险验证。** 先运行与修改直接相关的检查，再决定是否扩大验证范围。
8. **如实交付。** 说明行为变化、检查结果和未验证事项，不声称执行过未运行的检查。

## 代码组织与接口

### 模块和依赖

- 以职责、变更原因和调用关系划分模块，避免万能 `utils.py` 和重复的转发层。
- 尽量让核心逻辑独立于文件、网络、数据库和界面；通过参数传入必要依赖。
- 简单功能无需预先搭建多层架构，也不为每个函数单建一个文件。
- 文件变长时检查职责混杂、重复和导航困难；行数仅作提醒，不机械拆分。
- 显式导入所需名称，避免通配符导入；解决循环依赖应先检查职责和依赖方向。
- 模块导入时避免启动任务、连接网络或修改外部状态；副作用放到明确入口。

### 接口和数据

- 函数名称说明行为，参数名称说明含义；布尔开关过多时重新审视接口职责。
- 公共接口说明返回值、异常、可空性和关键副作用，修改前检查调用者。
- 结构固定的数据优先使用已有模型、`dataclass` 或 `TypedDict`，避免多层任意字典。
- 字典适用于实际键值映射；不要为简单数据引入不必要的模型框架。
- 区分“缺失”“空集合”“失败”等语义，不让同一个返回值承载无法区分的状态。
- 不用可变对象作为默认参数；共享可变状态必须有明确的生命周期和修改入口。
- `Protocol` 和抽象基类用于明确的结构契约或实现替换；依赖注入容器仅在实际复杂度需要时引入。

## Python 专项

### 类型与边界

- 为新增或修改的公共接口、核心函数补充类型；复杂局部变量按理解需要标注。
- 类型语法与项目支持的 Python 版本一致，不默认使用最新版本能力。
- 类型标注不执行运行时校验；配置、文件、请求等外部输入仍需验证并转换。
- 验证集中在信任边界，覆盖必要的类型、范围和字段关系，避免在内部层层重复。
- `Any` 限于不确定的外部边界，解析后尽早收窄；不靠大量忽略注释掩盖类型问题。
- 使用项目已有的 mypy、Pyright 或其他类型检查器实际检查相关代码。
- 尚未配置类型检查器时，不宣称类型已经验证，也不只为本次小改动引入整套工具链。
- `assert` 用于内部不变量，不用于必须始终执行的输入校验或业务错误处理。

### 异常与资源

- 捕获可以处理的具体异常；重试、降级或转换错误时明确触发条件。
- 转换异常时保留原因，例如 `raise DomainError(...) from exc`；不要只返回空值。
- 顶层统一捕获异常必须保留诊断信息并返回真实失败状态，避免重复记录同一错误。
- 日志包含可定位上下文；不要输出密钥、令牌或不必要的完整敏感输入。
- 文件、连接、锁等资源使用 `with` 或 `async with`；其他资源在明确位置可靠清理。
- 流式读取和批处理按数据规模选择，不无条件把大文件或结果集全部载入内存。

### 可读性与并发

- 优先易追踪的控制流，避免嵌套推导式、冗长单行表达式和隐式状态切换。
- 元类、反射、动态修改属性和运行时注册仅用于真实需要，并集中封装边界。
- 装饰器明确其对签名、异常、缓存和副作用的影响，不隐藏关键业务流程。
- 注释解释原因、限制和不明显的契约，避免逐行复述实现。
- 沿用项目的同步或异步模型；不为局部功能随意引入新的事件循环或并发框架。
- 异步任务明确超时、取消和清理行为；不要在事件循环内直接执行长时间阻塞操作。
- 共享可变状态明确并发保护方式；性能调整先确认瓶颈，再评估复杂度收益。

### 环境与依赖

- 沿用现有虚拟环境、包管理器和项目声明，避免混用管理方式或修改全局环境。
- 添加依赖前检查标准库与现有依赖；引入依赖应对应明确需求，避免重复功能。
- 依赖声明与锁文件按项目既有流程同步，不手工随意修改工具生成的锁文件。
- 区分运行、开发和可选依赖；兼容范围遵循应用或库自身的发布策略。
- 不顺带升级依赖、Python 版本或框架；接口变化时核对实际安装版本和项目配置。

## 读取与修改流程

1. 读取适用的项目说明，以及与本次工作有关的配置和检查入口。
2. 用文件名、符号和错误信息搜索，定位实现、关键调用者和现有测试。
3. 按需读取类型、被调用接口和相邻分支，确认输入来源、状态变化及失败路径。
4. 在现有模式内实施最小完整修改；公共接口变化必须同步受影响的调用者。
5. 检查差异，排除无关改动、遗漏导入、兼容性变化和自动生成内容的误编辑。
6. 运行适当检查，根据结果修复，再简要报告完成情况。

- 独立搜索和读取可以批量执行；后续操作依赖前一步结果时按顺序执行。
- 避免反复读取同一未变化文件，也不要只看报错行就忽略必要上下文。
- 使用局部补丁，避免重新生成整份文件；按任务需要输出差异、结果或指定完整文件。
- 生成文件优先修改其来源，再使用项目生成流程更新。
- 模块职责、公开接口或检查命令变化时更新相关说明，不为小改动创建冗长文档。

## 验证

- 先找项目脚本、配置和 CI 中已有的命令，使用项目环境与相同参数约定。
- 常见候选包括 `python -m pytest <测试路径>`、Ruff 和 mypy／Pyright；仅使用已配置工具。
- 格式检查、静态检查和行为测试解决不同问题，不能互相替代。
- 行为变化或缺陷修复优先检查正常路径、边界条件及原失败场景。
- 为缺少覆盖且有真实风险的行为补充测试；文案、注释等低影响修改无需机械增加测试。
- 测试断言可观察行为，不照抄实现，也不以过度 mock 掩盖关键边界。
- 检查通过后，仅在新增改动、失败或未解决风险出现时重复或扩大验证。
- 环境或外部服务导致检查未完成时，写明实际命令、阻碍和未验证范围。

## 完成标准

- 请求的行为已实现，必要调用者与文档已同步，未留下未说明的占位实现。
- 变更可以局部理解，接口、数据模型和错误路径清楚，无无关重构。
- 适用检查已完成，或明确列出未完成的检查及原因。
- 交付说明包含修改结果、验证结果以及会影响使用的兼容性或环境限制。
- 衡量优化效果时看完成正确修改的总耗时与返工次数，不只比较代码行数或 token 数。
