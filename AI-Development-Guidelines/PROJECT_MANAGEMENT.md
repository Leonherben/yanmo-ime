# 项目管理通用 AI 协作规范

## 适用方式

本规范用于规划、推进和交付软件任务，适用于个人项目、小团队及已有团队。
目标是降低上下文、沟通和返工成本，让每轮工作都有明确边界与可验证结果。

- 用户明确要求、项目约定和实际约束优先；本文作为未明确事项的默认规则。
- 简单修改直接执行；只有多步、跨模块或存在依赖时才维护简短计划。
- 按任务读取相关章节，不要求每次加载全部规范、历史记录和整个仓库。
- 小任务可使用一条任务卡，不强制角色分工、固定工期或额外管理文档。
- [产品规范](PRODUCT_REQUIREMENTS.md)负责做什么、为什么和验收条件。
- [技术架构规范](TECHNICAL_ARCHITECTURE.md)负责系统组织与技术边界；语言、前端规范负责实现。

## 核心规则

1. **先定结果。** 用可观察行为定义目标，不用“完善”“优化”等词代替范围。
2. **按结果切片。** 每项任务形成可演示、可验证的最小完整变化。
3. **集中事实。** 目标、状态、决定各保留一个权威位置，其他位置用引用。
4. **控制上下文。** 提供相关入口、契约和约束，不重复灌入全部材料。
5. **持续推进。** 已授权且可逆的工作自主完成，必要决策才交给用户。
6. **及时暴露偏差。** 范围、依赖或验证变化时说明影响，不隐去困难。
7. **以证据收尾。** 代码存在、编译通过和任务验收是不同层次的结果。

## 目标、范围与优先级

### 开始前

- 用一句话写清目标对象、需要解决的问题及完成后的可观察结果。
- 区分本轮必须实现、可延后和明确不做的内容，避免模糊的无限扩展。
- 为必须项写出验收方式；不确定的需求标为假设，不能伪装成用户要求。
- 已有需求文档时引用对应段落；可选用 REQ-xxx 编号，不强制编号体系。
- 只有缺失信息影响正确性、范围或不可逆动作时，才请求用户决策。
- 可逆且低影响的实现细节沿用项目惯例，并在必要时简短说明假设。

### 排序与预算

- 优先交付核心流程、必要依赖和影响范围明确的缺陷，装饰性工作按价值安排。
- 高不确定性先做有边界的验证，明确要回答的问题和停止条件。
- 时间、费用或模型调用预算以实际约定为准，不编造期限或精确工作量。
- 需要估算时写清假设、区间和主要不确定因素，不能把估算当承诺。
- 预算不足时列出保留项、延后项及影响，由有权决定的人调整承诺范围。

## 任务拆分与依赖

### 切成可验收的工作

- 优先拆成贯穿必要界面、业务逻辑和数据的薄切片，使每步可独立观察结果。
- 不只按前端、后端或数据库拆任务；底层准备工作应标明服务哪个可验收切片。
- 拆分依据是独立验收、必要上下文和依赖关系，不按固定行数或文件数机械拆分。
- 一项任务只承担一个主要结果；实现与无关重构、格式化或清理分开。
- 每项任务至少有目标、边界、依赖、相关入口和验收条件，可选用 TASK-xxx 引用。
- 任务过大时按正常路径、必要异常路径或迁移阶段拆分，保留最终集成检查。
- 不将安全、数据一致性或必需错误处理拆成可无限延后的附加任务。

### 依赖与并行

- 标明先决条件、接口输入输出和负责集成的人或执行者，识别真正的阻塞关系。
- 只有边界清晰、修改冲突较低且能节省时间时才并行，不为并行而增加协调负担。
- 并行前约定文件归属、公共接口、禁止修改区域和交付证据。
- 共享文件或公共契约有变动时先同步，避免多个执行者各自建立不兼容版本。
- 单项通过后仍检查组合流程；模拟依赖验证只能证明约定范围内的行为。

## 执行与变更

### 每轮执行

1. 读取当前任务卡、相关规范及直接依赖，定位现有实现与可复用能力。
2. 检查工作区已有修改，保护他人工作，再执行本轮最小完整变更。
3. 运行与风险相称的检查，对照验收条件判断结果。
4. 更新实际状态、证据和下一步；没有新信息时不重复长篇汇报。

- 上下文不足时先检索定位，再读取必要片段；避免把整个目录交给模型猜测。
- 跨轮恢复时提供目标、已完成证据、未决问题和相关路径，不复制全部对话。
- 保持实现、验证和反馈相邻，尽早发现契约误解，避免堆积大量未验证改动。
- 不为已授权的可逆步骤反复请求确认；需要权限或外部决策时明确具体动作。

### 范围变化

- 新要求先比较原目标，说明涉及的任务、接口、验证及预算影响。
- 新增工作不能靠悄悄删除原需求抵消；调整优先级与承诺范围后同步任务卡。
- 执行中发现必要缺陷可在授权范围内修复，明显超出范围的改动单独记录。
- 重大技术选择引用已有决定或可选的 ADR-xxx，避免多处抄写不同版本。
- 决定改变时保留简短原因和影响，及时更新失效的计划与验收条件。

## 状态、风险与交接

### 状态必须有依据

| 状态 | 最少记录 |
| --- | --- |
| 待开始 | 目标、验收条件及已知依赖 |
| 进行中 | 当前步骤、已有产物和下一步 |
| 阻塞 | 具体事实、影响、已尝试措施和解除条件 |
| 待验证 | 已实现范围、尚缺的检查及原因 |
| 已完成 | 对应验收结果、证据位置和已知限制 |

- 在现有任务系统或简短记录中维护状态，选择一个事实来源，不另建重复台账。
- 风险只记录会影响交付的具体事项，包括触发条件、影响和应对方式。
- 阻塞时继续推进独立工作，不伪造测试结果或用无关产物冒充任务完成。
- 必须求助时一次给出背景、证据、可选方案、建议及需要决定的事项。
- 交接写清当前基线、修改文件、运行方式、实际检查结果和下一项操作。
- 未提交修改、临时方案和外部依赖要显式标注，接手者不应靠猜测恢复状态。

## 验证与完成标准

- 逐项对应验收条件，检查用户或调用方可观察的结果，不只确认文件已生成。
- 验证深度随风险调整：局部文档修改可检查内容，逻辑变化应验证相关行为。
- 优先使用现有检查，覆盖受影响的正常路径、关键边界和必要失败恢复。
- 构建或静态检查通过不能代替行为验收；必要时验证真实集成与目标环境。
- 完成报告给出实际执行的检查及结果；未执行、未通过和被环境阻止要区分。
- 检查失败时说明是否由本轮变更引起；无证据时保留不确定性。
- 必须项仍未实现或关键验收未完成时，状态保持进行中、待验证或阻塞。
- 达到验收后停止无关扩展，简要交付变更、证据、使用方式及剩余限制。

## 可复制任务卡

按规模删减字段；简单任务无需单独建文件，已有内容直接引用。

```markdown
### 任务：<名称，可选 TASK-xxx>
- 目标：<对象、问题、可观察结果>
- 需求依据：<相关文档段落或可选 REQ-xxx>
- 范围：<必须实现>；本轮不做：<边界>
- 入口与约束：<相关路径、现有契约、环境>
- 依赖与归属：<先决条件、修改边界、集成负责人>
- 验收：<操作或输入 → 预期结果；必要边界>
- 预算：<仅填写已约定限制或注明假设的估算>
- 状态与证据：<实际状态、产物路径、检查结果>
- 未决事项：<事实、影响、解除条件；无则省略>
- 下一步：<可直接执行的动作>
```
