# 技术架构通用 AI 辅助规范

## 适用方式

本规范适用于新项目、功能扩展、架构调整和维护修复。
目标是让人和 AI 用有限上下文理解系统，局部修改、验证并交付，减少反复重构。

- 项目需求、实际运行约束和现有约定优先；本文补充未明确的事项。
- 小项目可以合并角色和文档，不强制分层、微服务、多语言或特定设计方法。
- 按本次影响范围阅读和执行；局部修复无需重新设计整个系统。
- 本文不替代语言级安全规则，代码实现继续遵循对应开发规范。

## 核心规则

1. **需求先行。** 先明确用户行为、验收方式和真实约束，再确定结构。
2. **保持简单。** 优先沿用成熟路线；增加复杂度必须对应可说明的收益。
3. **局部可改。** 一类变化尽量集中在明确模块内，避免跨系统连锁修改。
4. **职责清楚。** 明确模块负责什么、依赖谁、哪些事情由调用方处理。
5. **契约显式。** 输入、输出、状态归属和失败语义可以独立理解。
6. **证据驱动。** 关键能力尽早用小样验证，性能判断依据测量。
7. **按需演进。** 有具体实现经验后提炼抽象，不为假想场景搭建框架。
8. **如实交付。** 分清设计、实现、验证和未覆盖部分，不把编译通过当功能完成。

## 架构输入与技术选择

- 先读取相关需求及验收条件，区分必须支持、明确不做和后续可能支持的内容。
- 列出实际约束：运行平台、数据规模、网络条件、交付方式及团队维护能力。
- 未确认的限制标为假设，并说明影响；不编造并发量、可用性或响应时间目标。
- 检查现有代码、依赖和部署能力，优先复用已经验证的做法。
- 技术选择比较满足需求所需的少量方案，记录收益、成本和关键取舍。
- 新依赖应解决具体问题，同时考虑兼容性、维护成本和替换难度。
- 拆分服务、增加中间件或引入新语言前，说明简单结构为何无法满足需求。
- 对不确定的关键能力先做小范围验证；记录环境、结果和结论的适用范围。
- 原型成功只证明已验证的路径；正式交付仍需补齐真实配置、失败处理和构建验证。

## 模块、接口与状态

### 职责与依赖

- 按职责和共同变化组织模块，使常见修改有明确落点。
- 不将无关职责堆进巨型文件，也不为单次转发制造大量微小文件。
- 明确调用方向和数据流，避免循环依赖以及跨模块直接修改内部状态。
- 默认使用显式依赖和直接调用；插件、注册机制和事件总线按实际需要引入。
- 共享代码应有真实复用价值；允许少量清晰重复，避免过早通用化。
- 公共入口保持稳定，内部结构允许演进；变更契约时检查所有受影响调用方。

### 接口契约

- 说明输入输出的类型和业务含义，以及空值、缺失值、边界值的语义。
- 声明副作用、前置条件和失败结果，避免依赖隐含调用顺序。
- 涉及并发时说明共享数据、同步方式和重复操作语义。
- 涉及长任务时明确超时、取消和清理行为，避免只取消等待而遗留任务。
- 对外接口按需要明确版本兼容、变更过渡和废弃方式；内部接口不机械加版本层。
- 使用现有类型和错误约定，不为每个模块发明一套协议。

### 数据与资源

- 每类数据具有明确所有者和事实来源，派生值尽量通过计算获取。
- 区分持久状态、临时状态和缓存，说明谁能写入、何时失效。
- 缓存应对应已知成本；采用时明确一致性要求、失效和容量限制。
- 资源具有明确创建、持有和释放责任，覆盖成功、失败与取消路径。
- 仅在需要持久化时设计存储模型，明确约束、事务边界及兼容要求。
- 涉及数据结构迁移时说明已有数据处理、验证和恢复路径，避免只验证空库。

## 边界、失败与部署适配

### 外部边界

- 平台能力和外部服务集中在适当适配层，避免其细节散落到业务流程。
- 在实际信任边界验证外部输入；内部层不重复堆叠相同校验。
- 根据需求划定身份、授权和数据访问边界，不以界面隐藏替代权限检查。
- 凭证通过项目约定的安全配置获取，不写入代码、日志或公开产物。
- 明确外部依赖不可用时的行为，禁止用模拟成功掩盖真实失败。

### 失败与恢复

- 将失败视为正常流程，区分可恢复问题、输入问题和实现缺陷。
- 错误信息足以定位模块和操作；日志避免记录秘密及不必要的敏感内容。
- 重试考虑次数、间隔和重复副作用；非幂等操作不可无条件自动重试。
- 异步和并发用于解决明确需求，同时定义顺序、容量及失败传播方式。
- 需要排队时考虑积压和过载；无需队列的流程保持直接。
- 为关键失败设计恢复入口，说明如何确认恢复有效。

### 构建与发布

- 沿用项目实际构建、打包和配置方式，确认产物能在目标环境运行。
- 区分开发、测试和生产所需配置，记录必填项及缺失时的行为。
- 发布验证覆盖启动、关键操作和本次受影响能力，避免仅检查进程存活。
- 按影响和可恢复性设计发布步骤、回滚或修复前进方案，不默认每次增加审批。
- 数据变更与代码发布协调，明确旧版本能否读取新数据以及回退限制。

## 验证与演进

- 用验收条件选择检查范围，分别确认静态检查、接口行为和实际使用路径。
- 优先验证跨边界交互及高风险失败，对已知缺陷保留能防止复发的验证。
- 性能目标来自真实需求；按端到端预算测量关键环节，再优化已识别的瓶颈。
- 不根据局部跑分推断整体性能，不用未经验证的吞吐量支持技术选择。
- 架构调整分步实施，每步保持可构建、可验证，并记录必要的兼容过渡。
- 在本次迁移范围内确认调用方已切换后，清理失效抽象和过渡代码，避免永久保留两套事实来源。

## AI 读取与交付

- 先读相关需求、模块入口、接口定义和项目命令，再按调用关系补充上下文。
- 保留简短模块表或架构图，说明职责、入口和依赖方向；同一事实只维护一处。
- 只为重要取舍记录架构决策，职责、契约或决策改变时同步对应内容。
- 提供可搜索的文件与符号位置，避免每次复制全量设计和代码。
- 修改前说明影响范围和假设；交付时说明实际变化、验证结果和遗留问题。
- 必要时用 REQ-xxx、TASK-xxx、ADR-xxx 关联需求、任务和决策，不强制额外编号体系。

## 完成标准

按本轮交付阶段使用以下标准：设计阶段检查方案与验证计划，实施阶段检查实际构建、行为和恢复结果。设计通过不等于功能验收通过；尚未实施的检查标为待实施，不适用项说明原因。

- [ ] 需求、验收和关键假设明确，设计能够说明如何满足它们。
- [ ] 模块职责、调用方向、接口和状态归属清楚，改动范围可解释。
- [ ] 本轮涉及实现时，受影响的正常、边界及失败路径完成适当验证。
- [ ] 本轮涉及实现时，项目实际构建与必要的运行检查通过，未验证范围明确列出。
- [ ] 涉及发布或数据变化时，恢复方式及其限制明确。
- [ ] 相关架构记录已更新，原型、占位和未完成能力没有伪装为可用功能。

## 架构决策记录模板

```markdown
# ADR-xxx：决策标题
- 状态：提议 / 采用 / 替代；关联需求或任务：
- 问题与验收：需要解决什么，如何判断有效。
- 约束与假设：已确认事实；尚待验证内容。
- 方案与决定：考虑的方案、选择及理由。
- 影响：模块、契约、数据、兼容性和维护成本。
- 验证：实际环境、方法、结果及未覆盖范围。
- 实施与恢复：步骤、适用条件、回退或修复方式。
- 后续：何时重新评估；替代决策链接。
```
