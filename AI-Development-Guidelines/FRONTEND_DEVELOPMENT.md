# 前端通用 AI 辅助开发规范

## 适用方式

本规范适用于网页及使用 Web 技术构建的界面，覆盖原型、新功能、维护和修复。
目标是减少 AI 定位、阅读、生成和返工成本，同时保持界面一致、交互完整和代码可维护。

- 项目明确要求、设计约定、支持环境和现有配置优先；本文提供未明确事项的默认规则。
- 沿用已有框架、语言、样式方案和包管理器，不为满足本文迁移技术栈。
- 先阅读核心规则，再按任务阅读有关章节；无需每次加载全部规范和代码。
- 原型与正式功能按各自验收范围实施，模拟能力和未接入功能应明确标注。
- 保留必要的类型、校验、错误处理和验证，不以省 token 为由降低正确性。

## 核心规则

1. **明确用户行为。** 确认触发方式、状态变化、结果和失败恢复路径。
2. **控制修改范围。** 使用局部补丁，不顺带重设计页面、改名或格式化无关代码。
3. **优先复用。** 先查已有组件、设计变量、请求封装和交互模式，再增加实现。
4. **让上下文集中。** 相关组件、类型、样式和逻辑就近组织，减少无必要的跨文件追踪。
5. **让契约明确。** 输入、事件、数据结构、状态归属和副作用可独立理解。
6. **保持实现直接。** 按真实职责拆分，不预先建立复杂框架或大量微小组件。
7. **验证实际体验。** 构建检查、行为验证和页面观察分别执行，按改动风险选择范围。
8. **如实交付。** 说明变化、实际检查结果和未验证范围，不把模拟结果当作真实能力。

## 代码组织与接口

- 按功能和变更关系组织代码，沿用项目目录；不强制所有项目采用相同分层。
- 页面组织流程，组件承载明确的展示或交互职责；复杂逻辑按实际需要分离。
- 文件长度用于提醒职责是否混杂，不设机械行数上限，也不为每段模板创建组件。
- 通用组件应有真实复用价值；功能专用组件可以保留业务语义，不追求过度通用。
- 组件参数和事件使用可搜索的名称；避免含义模糊的布尔开关组合及多层纯转发。
- 优先显式依赖和直接调用；动态注册、反射或自定义语法必须解决实际问题。
- 公共接口变化时检查调用方；避免通过全局选择器、内部 DOM 结构等隐式方式耦合组件。
- 注释解释交互原因、限制和不明显的契约，不逐行复述模板或样式。
- 保留简短的页面、模块入口及开发命令说明，职责或入口变化时同步更新。

## 前端专项规则

### 样式与布局

- 优先复用已有颜色、字号、间距、圆角、层级和动效变量，避免散落重复的任意值。
- 组件样式保持合理作用范围；全局样式只承担明确的全局职责。
- 不通过不断增加选择器权重或叠加覆盖规则修补问题，先确认样式来源及布局原因。
- 按目标窗口尺寸设计伸缩、换行、滚动和溢出；常规布局优先使用正常文档流、Flex 或 Grid。
- 固定定位、绝对定位和固定尺寸用于适合的场景，避免依赖单张截图的像素位置。
- 对实际可能出现的长文本、空内容、较多数据和字体缩放检查布局，不只使用理想样例。
- 保持同类控件的尺寸、反馈和操作方式一致；需求未涉及的视觉区域保持稳定。
- 使用项目已有资源和图标约定，避免引入重复组件库、样式体系或未经确认的远程资源依赖。

### 状态与异步行为

- 每项数据保持明确的事实来源；可以可靠推导的值尽量不另存一份状态。
- 局部状态留在最近的合理位置；只有实际跨区域共享时才引入共享状态机制。
- 区分表单草稿、持久数据、请求状态和展示状态，避免互相覆盖。
- 请求明确加载、成功和失败结果；空数据作为独立语义处理，不伪装成加载或错误。
- 根据交互处理重复提交和请求竞态，避免旧响应覆盖较新的用户意图。
- 组件退出、参数变化或任务取消时，按框架机制清理监听器、定时器、订阅及相关任务。
- 副作用放在框架约定的位置，避免在可重复执行的渲染逻辑中直接写入外部状态。
- 超时、取消、重试和缓存按需要设计；自动重试应考虑次数、重复操作及服务端语义。

### 接口、数据与边界

- 沿用已有请求层和错误约定；视图不散落重复的地址拼接、认证处理和响应解析。
- 明确请求参数、返回数据、缺失值和错误结构，不凭空编造后端字段或接口能力。
- TypeScript 项目实际运行已配置的类型检查；JavaScript 项目沿用已有契约表达方式。
- 必要时使用 JSDoc 或明确的数据模型，不为本轮局部任务强制迁移语言。
- 静态类型不能验证实际网络响应；在适当边界检查不可信数据，避免内部层层重复验证。
- 保留服务端错误与前端校验的区别，向用户提供可理解且可恢复的反馈。
- 前端校验改善交互，权限和可信业务约束仍由服务端或可信执行边界实施。
- 不将私有服务密钥等秘密放入客户端代码或构建产物；公共配置与秘密明确区分。
- 展示外部内容时使用框架安全的文本机制；确需渲染 HTML 时采用明确的可信来源或净化策略。

### 交互与可访问性

- 按真实流程覆盖必要的加载、空数据、失败、成功、禁用和校验状态，无需为无关状态添加界面。
- 按钮、链接和菜单应执行所表达的行为；尚未实现的功能应隐藏、禁用或明确标注。
- 优先使用语义化元素；按钮执行操作，链接承担导航，表单控件具有可识别的标签。
- 图标按钮提供可访问名称；重要信息不只依赖颜色、悬停或装饰图形表达。
- 保持键盘可操作和焦点可见；弹层按所用模式处理初始焦点、关闭方式及焦点返回。
- 校验失败应定位问题并尽量保留用户输入；异步反馈避免无意义地打断操作或抢夺焦点。
- 按支持范围检查缩放、文本对比和减少动效偏好，避免阻碍阅读与操作。
- 对路由切换、刷新、返回和状态恢复，仅在产品需要的范围内明确行为并验证。

### 性能、构建与依赖

- 优先排查重复请求、不必要的资源加载、明显阻塞和无界列表，再考虑更复杂的优化。
- 缓存、记忆化、虚拟列表和代码拆分基于实际规模或测量结果采用，并考虑状态失效问题。
- 遵循目标浏览器或运行容器的支持范围；使用新能力前检查兼容性与必要的回退方式。
- 沿用包管理器、锁文件和构建配置；新增依赖对应明确需求，不顺带升级工具链。
- 不直接维护压缩包、构建产物和其他生成文件；修改来源后通过现有流程生成。
- 日志和诊断信息应有定位价值，避免泄露秘密或完整敏感数据。

## 原型与正式开发

- 原型可以使用模拟数据，模拟入口应集中且容易替换，并说明尚未验证的能力。
- 模拟数据覆盖所需状态及边界，不只展示成功路径；不要让真实失败退回假成功数据。
- 原型交互可以先简化，组件职责、样式变量和数据契约应尽量清楚。
- 继续用于正式开发前，确认真实接口、权限、持久化、目标环境和失败恢复行为。
- 不把按钮可点击、静态页面相似或演示流程成功视为系统能力已经实现。

## 读取与修改流程

1. 阅读适用项目说明，确认目标行为、支持环境和验收范围。
2. 搜索相关页面、组件及调用者，检查附近的样式变量、状态来源和已有测试。
3. 按需读取接口类型、请求实现和关键父子关系，不默认遍历全仓或整个组件库。
4. 在现有模式内实施最小完整修改，同步必要调用者与状态处理。
5. 检查差异，排除无关样式、依赖、锁文件和生成内容的变化。
6. 运行相关检查，实际观察并操作受影响界面，依据结果修复。

- 独立检索可以批量执行；涉及依赖关系的修改与验证按顺序进行。
- 避免反复读取未变化的长文件，也不以节省上下文为由猜测框架或接口行为。
- 使用局部补丁，避免因小修改重新生成整页；交付时不重复粘贴已保存的完整文件。

## 验证

- 优先使用仓库脚本、已有工具及 CI 约定，执行与变更相关的类型、lint、构建或测试检查。
- 检查受影响页面及必要的集成路径；构建成功不能代替浏览器或目标容器中的实际检查。
- 在目标窗口尺寸观察对齐、换行、遮挡、滚动和溢出，按风险覆盖不同尺寸与目标环境。
- 操作关键流程，检查所需失败状态、键盘操作以及相关控制台和网络错误。
- 截图用于发现视觉问题；请求、焦点、表单和导航等动态行为仍需实际操作。
- 行为变化和缺陷修复按风险增加回归测试；低影响文案或样式修改不机械新增测试。
- 测试关注可观察行为，避免复制实现或只验证模拟数据；优先复用已有测试设施。
- 检查通过后，仅在新增改动、失败或未解决风险出现时重复或扩大验证。
- 无法启动、缺少接口或无法访问目标环境时，明确报告阻碍和未验证范围，不宣称体验已验证。

## 完成标准

- 请求涉及的界面和行为已完成，相关调用者、状态及说明保持一致。
- 组件职责、数据来源和接口清楚，修改可局部理解，没有新增无理由的复杂度。
- 视觉遵循已有约定，必要状态、目标尺寸和交互路径已按范围验证。
- 模拟数据、真实能力和未完成事项可区分，未通过占位内容掩盖缺失功能。
- 交付说明包含变化、实际检查结果及剩余限制，区分通过、未执行和仍失败的检查。
- 以完成正确修改的总耗时和返工次数衡量效率，不单独追求更少的文件、行数或 token。
